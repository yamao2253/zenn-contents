# Zenn記事ネタ帳

Since: November 25, 2026

## 1. 目的

既存のZenn記事や技術学習、実機検証の過程で得られた知見から、新たな記事の題材を発掘・蓄積する。

記事を書くために新しい技術や開発環境を増やすのではなく、一つの技術を学習する過程から複数の価値ある記事を生み出すことを基本方針とする。

また、ChatGPTとMuseで本ファイルを共有し、異なる観点から記事候補の発掘、評価、優先度の見直しを行う。

## 2. 基本方針

- 本来の技術学習や開発を優先する。
- 既存の開発環境と実機検証結果を積極的に活用する。
- 読者が再現できる記事を目指す。
- 既存記事から切り出す場合は、独立した記事としての価値を明確にする。
- 既存記事の内容を単純に分割し、情報を薄めることは避ける。
- 読者獲得への期待と、技術者としての特色を伝える価値を分けて評価する。
- 実機確認済みの内容と追加検証が必要な内容を区別する。
- 閲覧数だけを理由に、本来の学習テーマや開発方針を変更しない。
- AI間で評価が異なる場合も、有用な観点は残す。
- 優先度は固定せず、開発の進捗や記事の閲覧状況に応じて見直す。
- 評価が分かれた候補は、各候補の詳細に「評価メモ」として両論を併記する（002、006で実施）。
- 公開した候補は8節に記録し、公開後30日時点の表示回数を備考に残す。分類ごとの伸び方の検証に使う（表示回数は毎朝集計している）。

## 3. 記事の分類

| 分類 | 目的 | 題材の例 |
|---|---|---|
| 本編 | 体系的な技術学習 | Try Kernel、Zephyr、Pico SDK |
| 実践ノウハウ | 汎用的な技術や開発手法の活用 | Gitバージョンの埋め込み |
| トラブル解決 | 具体的な問題の解決 | GDBの文字化け、環境構築時のエラー |
| 技術探究 | 技術の仕組みや内部動作の理解 | ELF、CPUレジスタ、UARTトレース |

### 3.1 優先度

| 優先度 | 意味 |
|---|---|
| S | 特に記事化を推奨する題材 |
| A | 記事化する価値が高い題材 |
| B | 技術的な価値があり、今後の学習と合わせて記事化したい題材 |
| C | 条件が整った場合に記事化を検討する題材 |

優先度は公開順序を強制するものではない。

### 3.2 評価の観点

- 読者獲得：対象読者の広さ、検索されやすさ、困りごとの具体性
- 技術的特色：技術者としての経験や理解の深さを伝えられるか
- 汎用性：特定のマイコン、OS、SDKに依存しない知見か
- 検証状況：既存の実機検証結果をどの程度活用できるか
- 工数：追加検証や記事執筆に必要な作業量
- 関連性：既存記事や今後のシリーズとの関係

読者獲得への期待は、実際の検索需要や競合記事を調査した結果ではなく、題材の性質から判断した仮説である。

### 001. Gitバージョンのファームウェアへの埋め込み

- 優先度：S
- 分類：実践ノウハウ
- 出典：[pico-trykernel-uart-trace.md](../articles/pico-trykernel-uart-trace.md)
- 該当箇所：4. Gitのバージョンを起動時に表示する
- 元記事の状態：未公開

#### タイトル案

MakefileでGitのコミットIDをファームウェアに埋め込む — 不要な再ビルドも防ぐ

#### 記事の狙い

実機で動作しているファームウェアが、どのGitコミットに対応しているのかを起動ログから確認できるようにする。

PicoやTry Kernelに限定されず、組込み開発全般に応用できる。

特に、生成するヘッダの内容が変化した場合だけファイルを更新し、不要な再コンパイルを防ぐ仕組みに実践的な価値がある。

#### 確認済みの内容

- `git describe --tags --always --dirty`によるバージョン取得
- Makefileによる`version.h`の自動生成
- 一時ファイルと既存ヘッダの内容比較
- 内容が変化した場合だけヘッダを更新する実装
- オブジェクトファイルと生成ヘッダの依存関係の設定
- UART起動ログへのバージョン表示

#### 追加検証

- 初回ビルド時のヘッダ生成
- 変更なしで再ビルドした場合の動作
- ソースコード変更時の`-dirty`の付加
- Gitコミット後のバージョン情報の更新
- Makefileが使用するシェルと各コマンドの実行環境

#### 補足

`-dirty`は未コミットの変更内容そのものを識別するものではない。

同じコミットから異なる変更を加えた場合でも、同じバージョン文字列になる可能性がある。

#### 公開方針

元記事が未公開のため、独立記事として先行公開することも可能。

ChatGPTによる今回の棚卸しで最も記事化を推奨する題材。

#### 評価メモ

ChatGPTとClaudeが独立した棚卸しで、ともにイチオシ（S）に挙げた。評価の軸が異なる2つのAIが独立に同じ題材を1位にしたことは、この候補への信頼度を上げる材料になる。

### 002. GDBのfinishと呼び出し元の変数への代入

- 優先度：S
- 分類：技術探究
- 出典：[pico-gdb-breakpoint-step.md](../articles/pico-gdb-breakpoint-step.md)
- 該当箇所：finishで戻った時点で、変数への代入は終わっている？

#### タイトル案

GDBで関数から戻ったのに変数が更新されない？ C言語の1行を機械語で追う

#### 記事の狙い

C言語では1行で記述される関数呼び出しと戻り値の代入が、CPUではどのような命令として実行されるのかを理解する。

#### 確認済みの内容

- `finish`で関数から戻ると、戻り値が確認できる。
- 今回の実行結果では、`finish`直後に呼び出し元の変数への代入は完了していなかった。
- `next`で実行を進めると、変数に戻り値が代入された。

#### 追加検証

- 関数呼び出し前後の逆アセンブル
- Armの関数呼び出し規約
- 戻り値を格納するCPUレジスタ
- 戻り値を変数に代入する命令
- 命令単位のステップ実行による確認

#### 公開方針

GDBシリーズのCPUレジスタやアセンブリ命令単位のデバッグと関連が深い。

独立記事とするか、シリーズの一部に組み込むかは、残りの記事構成を確認してから判断する。

#### 評価メモ

- ChatGPT：S。逆アセンブル、関数呼び出し規約、戻り値レジスタへ発展させられる点を評価。
- Muse：題材自体の面白さは認めるが、GDBシリーズ残り回（CPUレジスタを扱う回）の題材と重なるため、単独の切り出しには慎重。シリーズへの組み込みを優先する視点で、独立した優先度は最下位に置いた。
- 統合見解：優先度Sは維持する。ただし最初に決めるべきは優先度ではなく公開形態（独立記事か、シリーズ組み込みか）であり、シリーズ構成の確定後に判断する。

### 006. GDBのOS ABI警告の解消

- 優先度：A
- 分類：トラブル解決
- 出典：[pico-gdb-multiarch-windows-env.md](../articles/pico-gdb-multiarch-windows-env.md)
- 該当箇所：Windows OS ABIの警告を解消する

#### タイトル案

Windows版GDB MultiarchのOS ABI警告を解消する — set osabi noneと-iex

#### 記事の狙い

Windows上のGDB Multiarchでベアメタル向けELFを読み込む際に発生するOS ABI警告の原因と対処方法を説明する。

警告メッセージ：

`warning: A handler for the OS ABI "Windows" is not built into this configuration`

#### 確認済みの内容

- `show osabi`による設定確認
- `set osabi none`による設定変更
- ELF読み込み後に設定しても、既に発生した警告は消えないこと
- `-iex`によるELF読み込み前の設定
- 警告が表示されなくなること

#### 追加検証

- `-ex`と`-iex`の実行タイミングの比較
- 設定を変更する前後の動作確認

#### 公開方針

ただし、元の文字化け対策記事は比較的よく読まれているため、単純な切り出しによって情報を薄めないようにする。

独立させる場合は、GDBの起動時の処理順序など、元記事にない追加価値を持たせる。

候補015との統合も検討する。

#### 評価メモ

- ChatGPT：A（短編候補）。元の文字化け対策記事がよく読まれているため、細分化して内容を薄めることへの注意を重視。
- Muse：S相当。警告文そのものが検索キーワードになるexact-match型であり、元記事内で約90行で完結していて追加検証がほぼ不要なため、短編の本命と評価した。
- 統合見解：優先度はAとする。ただし公開の順序としては、001の次に短編として早期公開する実験枠とする。公開の条件は、015との統合と、「-exと-iexの実行タイミングの比較」という元記事にない追加価値を付けること。トラブル解決型の伸び方は、表示回数の毎朝集計で観察する。

## GDBを終了せずに画面をクリアする - shell

GDBの`shell`コマンドを使用すると、GDBを終了せずに、
ホストOS側のシェルコマンドを実行できます。

Windows環境で画面をクリアするには、次のように入力します。

​```gdb
shell cls
​```

画面表示がクリアされますが、ブレークポイントの設定や
プログラムの停止位置など、デバッグ状態には影響しません。

なお、GDBの`clear`は画面をクリアするコマンドではなく、
ブレークポイントを削除するコマンドです。
