# はじめに

CQ出版社『Interface』2023年7月号の特集「ラズパイPicoで1500行 ゼロから作るOS」を読み進めながら、Raspberry Pi PicoでTry Kernelを動かしています。

これまでに、Windows 11上でOpenOCDとGDBを使ったデバッグ環境を構築しました。

今回は、この環境を使って、プログラムを停止させて **変数の値を調べたり、値の変化を検出したりする方法** を学びます。

単にGDBのコマンドを紹介するのではなく、実際のプログラムを題材に、何を確認したいのか、そのためにどう操作すればよいのかを考えながら進めます。

# 使用環境

| 項目 | 内容 |
|---|---|
| OS | Windows 11 |
| シェル | PowerShell 7 |
| ターゲット | Raspberry Pi Pico W（RP2040） |
| デバッグ接続 | CMSIS-DAP / SWD |
| OpenOCD | xPack OpenOCD 0.12.0-7.1 |
| GDB | MSYS2 GDB Multiarch |
| デバッグ対象 | Try Kernel（`part_4/sect_3`） |

Try Kernelのビルド環境とOpenOCD/GDBによるデバッグについては、以下の記事で紹介しています。

- [「ラズパイPicoで1500行 ゼロから作るOS」を2026年に動かす](https://zenn.dev/helowota/articles/pico-trykernel-windows-env)
- [OpenOCDとGDBでRaspberry Pi Picoをデバッグする](https://zenn.dev/helowota/articles/pico-openocd-gdb-debug)

今回はソースコードを変更せず、GDBからプログラムの動作を観察します。

# デバッグの手がかりは変数の値

プログラムが思いどおりに動かないとき、原因を調べる手がかりの一つが**変数の値**です。

例えば、関数の戻り値は正しいのか、その値が変数に格納されているのか、どのタイミングで値が変化するのか。

GDBには、変数の値を表示する`print`、プログラムが停止するたびに値を表示する`display`、値の変化を検出して停止する`watch`など、変数を調べるための機能が用意されています。

さらに、変数の型やサイズ、アドレスを調べたり、メモリの内容を直接確認したりすることもできます。

これらは似たような機能に見えますが、それぞれ役割が異なります。**現在の値を知りたいのか、停止するたびに値を確認したいのか、それとも値が変化した瞬間を捉えたいのか。目的や状況に応じて使い分けることが重要です。**

今回は、以前の記事「[Try Kernelのタスク管理 — なぜOSが必要なのか？](https://zenn.dev/helowota/articles/pico-trykernel-task-management)」で取り上げたタスク生成処理を題材に、これらの機能を実際に試しながら、**GDBで変数を調べる方法と、その使い分け**を学びます。

## 初期タスクの生成処理を調べる

Try Kernelの起動処理では、初期タスクを生成し、そのタスクを実行します。

書籍P.74の`kernel/inittsk.c`には、次の処理があります。

```c
ID tskid_ini;
```

```c
tskid_ini = tk_cre_tsk(&ctsk_ini);  // 初期タスク生成
tk_sta_tsk(tskid_ini, 0);           // 初期タスク実行
```

`tk_cre_tsk()`はタスクを生成するAPIで、その戻り値が`tskid_ini`に保存されます。

たとえば、Try Kernelを起動しても初期タスクが動かなかったとします。

原因としては、タスクの生成に失敗した、生成したタスクを正常に起動できなかった、起動後の処理で問題が発生した、といった可能性が考えられます。

そこで、まずは`tk_cre_tsk()`の戻り値をGDBで調べ、**初期タスクが正常に生成されたかどうか**を確認してみます。

---

# デバッグの準備

変数の値を調べる前に、OpenOCDとGDBを起動し、Raspberry Pi Pico Wにプログラムをロードします。

まず、PowerShell 7でOpenOCDを起動します。

```powershell
openocd -f interface/cmsis-dap.cfg -c "adapter speed 1000" -f target/rp2040.cfg
```

別のPowerShell 7で`part_4/sect_3`ディレクトリに移動し、GDBを起動します。

```powershell
gdb-multiarch -q build/trykernel.elf
```

GDBからOpenOCDに接続し、プログラムをロードします。

```gdb
target remote localhost:3333
monitor reset halt
load
```

これで、GDBからプログラムの実行を制御する準備ができました。

# 実際にGDBで変数を追いかける

まずは、`tk_cre_tsk()`の実行前後で`tskid_ini`の値を比較し、タスク生成の結果を確認してみます。

## 1. どこでプログラムを停止すればよいか？

`tk_cre_tsk()`の戻り値を調べるには、関数の実行前後でプログラムを停止させる必要があります。

GDBでは、ブレークポイントとステップ実行を組み合わせることで、目的の場所でプログラムを停止できます。

まず、`main()`にブレークポイントを設定し、実行を再開します。

```gdb
break main
continue
```

実行結果：

```text
Thread 1 "rp2040.core0" hit Breakpoint 1, main () at kernel/inittsk.c:31
31          tskid_ini = tk_cre_tsk(&ctsk_ini);              // 初期タスク生成
```

`tk_cre_tsk()`が実行される直前で停止できました。

ここから、タスク生成処理の前後で変数の値を比較していきます。

## 2. 変数の値を表示する - print

プログラムが停止したところで、`tskid_ini`の値を調べます。

GDBには、変数や式の値を表示する`print`コマンドがあります。

まず、タスク生成前の値を確認します。

```gdb
print tskid_ini
```

実行結果：

```text
$1 = 0
```

`tskid_ini`の値は`0`でした。

続いて、`next`でタスク生成処理を1行実行します。

```gdb
next
```

実行結果：

```text
32          tk_sta_tsk(tskid_ini, 0);                       // 初期タスク実行
```

`next`は、呼び出した関数の内部に入らず、呼び出し元の次の行まで実行するコマンドです。

ここで、もう一度変数の値を確認します。

```gdb
print tskid_ini
```

実行結果：

```text
$2 = 1
```

**`tskid_ini`の値が`0`から`1`に変化しました。**

`tk_cre_tsk()`の実行によって、戻り値`1`が`tskid_ini`に格納されたことが分かります。

Try Kernelでは正のタスクIDが生成成功を示すため、今回のタスク生成は成功したと判断できます。

ただし、タスク生成に成功したことと、実際にタスクが動作したことは別です。後者を確認するには、さらに調査が必要です。

## 3. 変数の値を自動表示する - display

変数の値を何度も確認する場合、毎回`print`を入力するのは面倒です。

GDBには、プログラムが停止するたびに指定した式の値を自動表示する`display`コマンドがあります。

```gdb
display tskid_ini
```

実行結果：

```text
1: tskid_ini = 1
```

これで、`tskid_ini`が自動表示の対象に登録されました。

### 実行を進めるとどうなるか？

続いて、`next`で実行を進めてみました。

```gdb
next
```

ところが、今回は次の行で停止せず、GDBのプロンプトも戻ってきませんでした。

`tk_sta_tsk()`はタスクの実行を開始するAPIです。内部ではスケジューラも呼び出されるため、単純な関数呼び出しとは異なる動作になります。

そこで、`Ctrl+C`で実行を中断しました。

実行結果：

```text
Thread 1 "rp2040.core0" received signal SIGINT, Interrupt.
0x00000030 in ?? ()
1: tskid_ini = 1
```

停止時に、`tskid_ini = 1`が自動表示されています。

**`display`は、プログラムの実行中に値をリアルタイム表示する機能ではなく、GDBが停止したタイミングで値を表示する機能**です。

なお、今回の中断時には、プログラムカウンタが`0x00000030`を指していました。バックトレースでは`tk_sta_tsk()`と`set_primask()`が確認できましたが、このアドレスに到達した理由までは調査していません。

今回は変数の観察が目的なので、ここでは深追いせず、次の実験に進みます。

## 4. 変数の値が変化したら停止する - watch

ここまでは、プログラムを停止させてから変数の値を調べていました。

では、変数が書き換わったことをきっかけに、プログラムを停止できないでしょうか？

GDBには、そのためのウォッチポイントがあります。

今回は `watch` コマンドを使い、`tskid_ini` の値が変化する場面を観察します。

### タスク生成前まで戻す

最初から実行し直すため、RP2040をリセットします。

```gdb
monitor reset halt
continue
```

実行結果：

```text
Thread 1 "rp2040.core0" hit Breakpoint 1, main () at kernel/inittsk.c:31
31          tskid_ini = tk_cre_tsk(&ctsk_ini);              // 初期タスク生成
1: tskid_ini = 0
```

先ほど設定したブレークポイントと`display`は残っているため、再設定する必要はありません。

なお、プログラムを書き換えていないので、今回は`load`も不要です。

### ウォッチポイントを設定する

`tskid_ini`を監視対象に設定します。

```gdb
watch tskid_ini
```

実行結果：

```text
Hardware watchpoint 3: tskid_ini
```

今回は、ハードウェアウォッチポイントが設定されました。

続いて、プログラムの実行を再開します。

```gdb
continue
```

実行結果：

```text
Thread 1 "rp2040.core0" hit Hardware watchpoint 3: tskid_ini

Old value = 0
New value = 1
0x10000942 in main () at kernel/inittsk.c:32
32          tk_sta_tsk(tskid_ini, 0);                       // 初期タスク実行
1: tskid_ini = 1
```

**`tskid_ini`の値が`0`から`1`に変化したことを検出し、自動的に停止しました。**

`Old value`と`New value`によって、変更前後の値も確認できます。

今回は書き込み箇所が分かっていましたが、意図せず変数が書き換わる不具合では、ウォッチポイントが特に役立ちそうです。

### `print`、`display`、`watch`の違い

| コマンド | 用途 |
|---|---|
| `print` | 現在の変数の値を表示する |
| `display` | プログラムが停止するたびに値を自動表示する |
| `watch` | 監視対象の値が変更されたときに停止する |

似ているようですが、役割はそれぞれ異なります。

今回のように、**確認したい内容に応じて使い分ける**ことが重要です。

## 5. 変数の型・サイズ・アドレス・メモリを確認する - ptype / sizeof / & / x

C言語では変数名を使って値を参照しますが、実際にはメモリ上にデータが格納されています。

GDBでは、変数のアドレスを調べたり、そのアドレスのメモリを直接表示したりできます。

ここでは、`tskid_ini`がどこに、どのような形式で格納されているかを調べます。

### 型を確認する - ptype

変数の値をメモリ上で確認する前に、型とサイズを調べておきます。

まず、`ptype`コマンドで変数の型を確認します。

```gdb
ptype tskid_ini
```

実行結果：

```text
type = int
```

`tskid_ini`は`ID`型として宣言されていますが、GDBでは基本型の`int`として表示されました。

このあと、変数のサイズとアドレスを調べ、メモリ上にどのように格納されているかを確認します。

### サイズを確認する - sizeof

続いて、`sizeof`演算子で変数のサイズを確認します。

GDBでは、デバッグ対象のプログラミング言語に応じた式や演算子を使用できます。今回のデバッグ対象はC言語なので、C言語の`sizeof`演算子を使用できます。

`sizeof`はGDB独自のコマンドではなく、`print`コマンドで評価する式の一部です。

```gdb
print sizeof(tskid_ini)
```

実行結果：

```text
$3 = 4
```

今回の環境では、`tskid_ini`のサイズは4バイトであることが分かりました。

### アドレスを確認する - &

続いて、変数が格納されているメモリのアドレスを確認します。

C言語のアドレス演算子`&`を使用すると、変数のアドレスを取得できます。`sizeof`と同様に、GDBの`print`コマンドでC言語の式を評価しています。

```gdb
print &tskid_ini
```

実行結果：

```text
$4 = (ID *) 0x20000164 <tskid_ini>
```

`tskid_ini`は、RP2040のSRAM領域にある`0x20000164`に配置されています。

変数の値は`1`ですが、その値を格納しているメモリのアドレスは`0x20000164`です。

### メモリの内容を調べる - x

まず、4バイトを1バイトずつ表示してみます。

```gdb
x/4xb &tskid_ini
```

実行結果：

```text
0x20000164 <tskid_ini>: 0x01    0x00    0x00    0x00
```

`x/4xb`は、指定したアドレスから4個のデータを、16進数・1バイト単位で表示する指定です。

続いて、同じメモリを4バイトまとめて表示します。

```gdb
x/wx &tskid_ini
```

実行結果：

```text
0x20000164 <tskid_ini>: 0x00000001
```

同じメモリを表示していますが、データの見え方が異なります。

RP2040はリトルエンディアンなので、32ビット値`0x00000001`の最下位バイト`0x01`が、最も低いアドレスに格納されています。

このように、`print`ではC言語の変数として値を確認でき、`x`ではメモリに格納されているデータを直接確認できます。

# 今回分かったこと

今回は、Try Kernelの初期タスク生成処理を題材に、GDBで変数の値を調べました。

実機で確認できた内容をまとめます。

| 確認したこと | GDBコマンド | 結果 |
|---|---|---|
| タスク生成処理の前後で停止 | `break`、`next` | `main()`の31行目と32行目で停止 |
| 変数の値を表示 | `print` | `0`から`1`に変化 |
| 変数の値を自動表示 | `display` | 停止時に`tskid_ini = 1`を表示 |
| 変数の変更を検出 | `watch` | `Old value = 0`、`New value = 1` |
| 型とサイズを確認 | `ptype`、`sizeof` | `int`、4バイト |
| アドレスとメモリを確認 | `print &`、`x` | `0x20000164`に`0x00000001`を格納 |

`tk_cre_tsk()`の戻り値が`tskid_ini`に格納されたことを確認でき、初期タスクの生成に成功していると判断できました。

また、変数を調べる方法にも、現在の値を見る、自動表示する、変更を検出して停止する、メモリを直接確認するといった違いがあることが分かりました。

**何を確認したいのかに応じてGDBの機能を使い分ける**ことで、効率よくデバッグを進められます。
