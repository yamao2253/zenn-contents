# Raspberry Pi Picoの起動処理

書籍P.50の図2では、Picoの起動処理を次の3段階に分けて説明しています。

1. ROM上のリセットハンドラを実行
2. XIPの設定
3. 例外ベクタテーブルの設定とユーザ定義リセットハンドラの実行

それぞれの段階で、CPUが実行するプログラムのメモリ領域が変化します。

| 段階 | 実行するプログラム | メモリ領域 |
|---|---|---|
| 1 | ファースト・ステージ・ブートローダ | Boot ROM |
| 2 | セカンド・ステージ・ブートローダ | SRAM |
| 3 | Try Kernelのリセットハンドラ | 外部フラッシュメモリ |

今回の学習では、このメモリ領域の移り変わりに着目します。

## メモリマップ

RP2040のメモリマップのうち、今回の起動処理に関連する領域を整理します。

| 開始アドレス | 終了アドレス | メモリ領域 |
|---|---|---|
| `0x00000000` | `0x00003fff` | Boot ROM（16KiB） |
| `0x10000000` | `0x101fffff` | 外部フラッシュメモリ（2MiB、XIP経由） |
| `0x20000000` | `0x20041fff` | SRAM（264KiB） |

Boot ROMはRP2040の内部にあり、ユーザが書き換えることはできません。

一方、Try Kernelのプログラムは外部フラッシュメモリに格納されています。

電源投入時に実行されるのは、Try Kernelのプログラムではなく、Boot ROMに格納されたプログラムです。

# ファースト・ステージ・ブートローダの実行

書籍P.50の図2（a）に相当する処理です。

ファースト・ステージ・ブートローダでは、外部フラッシュメモリの先頭256バイトに格納されたセカンド・ステージ・ブートローダ（以降、boot2）をSRAMに転送します。

転送したboot2のチェックサムを検証した後、SRAM上のboot2に制御を移します。

## boot2の実体

Try Kernelの以下のファイルにboot2が定義されています。

`part_4/sect_3/boot/boot2.c`

このファイルは、ブートローダの処理をC言語で記述したものではありません。

Pico C/C++ SDKに由来する機械語を、256バイトの配列として定義したものです。

配列の先頭8バイトは次のようになっています。

```c
0x00, 0xb5, 0x32, 0x4b, 0x21, 0x20, 0x58, 0x60,
```

このデータが外部フラッシュメモリの先頭に配置され、起動時にSRAMへ転送されます。

## boot2の転送先

RP2040のBoot ROMのソースコードはGitHubで公開されています。

https://github.com/raspberrypi/pico-bootrom-rp2040

`bootrom/bootrom_main.c` では、boot2のサイズと転送先が次のように定義されています。

```c
#define BOOT2_SIZE_BYTES 256
#define BOOT2_BASE (SRAM_END - BOOT2_SIZE_BYTES)
```

SRAMの末尾256バイトがboot2の転送先になります。

```text
0x20042000 - 0x100 = 0x20041f00
```

したがって、boot2は次の領域に転送されます。

| 項目 | アドレス |
|---|---|
| 転送先の開始 | `0x20041f00` |
| 転送先の終了 | `0x20041fff` |

リセット直後のMSPの値も `0x20041f00` でした。

スタックはアドレスが小さくなる方向に使用されるため、boot2の転送先とBoot ROMが使用するスタック領域は重なりません。

### 結果と考察

事前の実機検証では、boot2の転送先の内容をGDBで確認しました。

先頭8バイトの内容は次のとおりです。

```text
0x20041f00:  0x4b32b500  0x60582021
```

RP2040はリトルエンディアンなので、バイト単位で見ると `boot2.c` の配列の内容と一致しています。

また、配列とメモリダンプを比較した結果、256バイトすべてが一致していました。

別途、転送先のデータを書き換えてから起動処理を実行し、ウォッチポイントによって新たにデータが書き込まれることも確認しています。

Boot ROMからboot2に制御を移す直前の命令は次のとおりです。

```asm
0x00002574: adds    r5, #1
0x00002576: mov     lr, r7
0x00002578: bx      r5
```

BX命令の実行直前には、R5に `0x20041f01` が設定されています。

BX命令を実行すると、PCは `0x20041f00` に変化します。

アドレスのbit 0はThumb状態の指定に使用されるため、実際の命令のアドレスは `0x20041f00` になります。

ここでCPUが再度リセットされるわけではありません。

BX命令によってPCが変更され、CPUが命令を読み出すメモリ領域がBoot ROMからSRAMに変化します。

# セカンド・ステージ・ブートローダの実行

書籍P.50の図2（b）に相当する処理です。

SRAM上に転送されたboot2では、外部フラッシュメモリ上のプログラムを効率よく実行するためのXIPの設定を行います。

## XIPとは

XIP（Execute-In-Place）は、外部フラッシュメモリに格納されたプログラムを、SRAMに転送することなく実行するための仕組みです。

RP2040の外部フラッシュメモリは、Quad SPIインタフェースで接続されています。

CPUからは、XIPの仕組みによって、外部フラッシュメモリを通常のメモリのようにアドレス空間上でアクセスできます。

| | boot2の転送時 | XIP設定完了後 |
|---|---|---|
| 外部フラッシュへのアクセス | CPUがSSIのレジスタを操作 | XIPハードウェアがアクセスを仲介 |
| データの扱い | CPUがSRAMに書き込む | メモリマップ上のアドレスからアクセス |
| プログラムの実行 | SRAMに転送したboot2を実行 | 外部フラッシュ上のプログラムを実行可能 |

XIPの設定中に外部フラッシュメモリから命令を読み出すことはできないため、boot2はSRAM上で実行します。

### 結果と考察

boot2のXIP設定処理の末尾には、次の命令があります。

```asm
0x20041f90: movs    r1, #1
0x20041f92: str     r1, [r3, #8]
```

このとき、R3にはSSIのベースアドレスである `0x18000000` が格納されています。

STR命令によって、SSIの有効化レジスタ（SSIENR）に1が書き込まれます。

事前の実機検証では、次の変化を確認できました。

| | SSIENR（`0x18000008`） |
|---|---|
| STR命令実行前 | `0x00000000` |
| STR命令実行後 | `0x00000001` |

この処理の後、外部フラッシュメモリ上のTry Kernelの例外ベクタテーブルを読み出すことができました。

```text
0x10000100 <vector_tbl>:  0x20040000  0x100007b5
```

この時点ではPCはまだSRAM上のアドレスを指しています。

# 例外ベクタテーブルの切り替え

書籍P.50の図2（c）に相当する処理です。

XIPの設定が完了すると、boot2は例外ベクタテーブルをBoot ROM上のものから外部フラッシュメモリ上のものに切り替えます。

## VTOR

Cortex-M0+には、例外ベクタテーブルの先頭アドレスを指定するVTOR（Vector Table Offset Register）があります。

RP2040では、VTORは次のアドレスに配置されています。

```text
0xe000ed08
```

VTORの値を変更することで、CPUが例外処理時に参照する例外ベクタテーブルを切り替えることができます。

## 2つの例外ベクタテーブル

Picoには、Boot ROM上の例外ベクタテーブルと、外部フラッシュメモリ上のユーザ定義の例外ベクタテーブルがあります。

両者の先頭2項目を比較します。

| | Boot ROM | Try Kernel |
|---|---|---|
| テーブルの先頭アドレス | `0x00000000` | `0x10000100` |
| MSPの初期値 | `0x20041f00` | `0x20040000` |
| リセットベクタ | `0x000000eb` | `0x100007b5` |

これらは実機で確認した値です。

boot2はTry Kernel側の例外ベクタテーブルの内容に従って、MSPとPCを設定します。

## boot2によるVTOR、MSP、PCの設定

boot2の末尾を逆アセンブルすると、次の命令が確認できます。

```asm
0x20041f9c: ldr     r0, [pc, #72]
0x20041f9e: ldr     r1, [pc, #76]
0x20041fa0: str     r0, [r1, #0]
0x20041fa2: ldmia   r0, {r0, r1}
0x20041fa4: msr     MSP, r0
0x20041fa8: bx      r1
```

最初の2つのLDR命令によって、R0とR1に次の値が設定されます。

| レジスタ | 設定値 | 意味 |
|---|---|---|
| R0 | `0x10000100` | Try Kernelの例外ベクタテーブルの先頭 |
| R1 | `0xe000ed08` | VTORのアドレス |

続く4命令によって、Try Kernelの起動に必要な処理が行われます。

| 命令 | 処理 |
|---|---|
| `str r0, [r1, #0]` | VTORの設定 |
| `ldmia r0, {r0, r1}` | MSPの初期値とリセットベクタの読み出し |
| `msr MSP, r0` | MSPの設定 |
| `bx r1` | Try Kernelのリセットハンドラへ分岐 |

この4命令が、書籍P.50の図2（c）で説明されている処理の具体的な実装です。

# ハードウェアによる初期化とソフトウェアによる初期化

前回の記事では、CPUのリセット直後の動作を確認しました。

CPUのリセット時には、ハードウェアによって例外ベクタテーブルの先頭2項目が読み出され、MSPとPCが設定されます。

一方、今回確認したboot2の終了処理では、ソフトウェアによって同様の処理が行われています。

| | CPUのリセット時 | boot2の終了処理 |
|---|---|---|
| 実行主体 | ハードウェア | ソフトウェア |
| 例外ベクタテーブル | Boot ROM | 外部フラッシュメモリ |
| テーブルの読み出し | ハードウェアによる処理 | LDMIA命令 |
| MSPの設定 | ハードウェアによる処理 | MSR命令 |
| PCの設定 | ハードウェアによる処理 | BX命令 |

Try Kernelのリセットハンドラが実行される際に、CPUが再度リセットされるわけではありません。

boot2が、ユーザ定義の例外ベクタテーブルに従って、リセット時の初期化に相当する処理を行っています。

そのため、Try Kernelから見ると、あたかも自身の例外ベクタテーブルに従って起動されたように見えます。

書籍P.50で説明されているこの動作を、実際のアセンブリ命令とレジスタの変化から確認することができました。

# 起動処理全体のレジスタの変化

今回の実機検証で確認したPC、SP、VTORの変化をまとめます。

| 観測点 | PC | SP | VTOR |
|---|---|---|---|
| リセット直後 | `0x000000ea` | `0x20041f00` | `0x00000000` |
| boot2転送完了 | `0x0000254a` | `0x20041ee8` | `0x00000000` |
| boot2への分岐直前 | `0x00002578` | `0x20041ee8` | `0x00000000` |
| boot2のPUSH命令実行後 | `0x20041f02` | `0x20041ee4` | `0x00000000` |
| XIP設定・POP命令実行後 | `0x20041f96` | `0x20041ee8` | `0x00000000` |
| VTOR設定・LDMIA命令実行後 | `0x20041fa4` | `0x20041ee8` | `0x10000100` |
| Try Kernelの実行開始 | `0x100007b4` | `0x20040000` | `0x10000100` ※ |

※ Try Kernelの実行開始時のVTORは、前後の実測値と命令列から判断した値です。

PCの変化に着目すると、次のようにメモリ領域が移り変わっていることが分かります。

```text
Boot ROM
  0x000000ea
       |
       | boot2の転送とチェックサムの検証
       | BX命令
       v
SRAM
  0x20041f00
       |
       | XIPの設定
       | VTORとMSPの設定
       | BX命令
       v
外部フラッシュメモリ（XIP）
  0x100007b4
  Try KernelのReset_Handler
```

# おわりに

今回は、CPUのリセットからTry Kernelのリセットハンドラが実行されるまでの起動処理を、GDBを使用して確認しました。

特に、次の点について理解を深めることができました。

- boot2がSRAMに転送され、実行される仕組み
- XIPの設定と外部フラッシュメモリ上のプログラムの実行との関係
- VTORによる例外ベクタテーブルの切り替え
- ソフトウェアによるMSPとPCの設定

PC、SP、VTORの変化を実際に観察することで、書籍の図2で説明されている起動処理を、CPUの具体的な動作として理解することができました。

次は、Try Kernelのプログラムがどのようにメモリ上に配置されているのか、リンカ・スクリプトとELFファイルに着目して学習を進めたいと思います。
