# Try Kernelのタスク管理 — なぜOSが必要なのか？

## はじめに

Raspberry Pi Picoを使って、OSを自作する「Try Kernel」。

CQ出版社『Interface』2023年7月号の特集「ラズパイPicoで1500行 ゼロから作るOS」を参考に、Try Kernelをビルドし、実機で動作させるところまで試してきました。

今回は少し視点を変えて、**作ったOSをアプリケーションから使ってみます。**

Try Kernelには、次の4つの主要機能が実装されています。

| 機能 | 役割 |
|---|---|
| タスク管理 | 複数の処理をタスクとして実行する |
| タスク付属同期 | タスクを待たせたり、起こしたりする |
| イベントフラグ | タスク間で情報を通知する |
| セマフォ | 共有資源へのアクセスを制御する |

これらは、小規模なマルチタスクアプリケーションを作るための基本的な機能です。

本記事では、最初の「タスク管理」を取り上げます。

なぜOSが必要なのか。普通のCプログラムと何が違うのか。そして、OSのタスク管理機能をどのように使うのか。

実際にTry Kernelを動かしながら考えていきます。

## OSがなくてもプログラムは動く

Raspberry Pi Picoでは、OSを使わなくてもC言語でプログラムを作れます。

例えば、LEDを点滅させるプログラムなら、無限ループの中でLEDのON/OFFを繰り返せば実現できます。

では、LEDを点滅させながら、ボタンの入力も監視したい場合はどうでしょうか。

これもOSがなくても実現できます。

LEDの制御とボタンの監視を1つのループの中で順番に実行すればよいのです。

しかし、処理が増えてくると、少しずつ難しくなります。

ある処理が長時間待っている間、ほかの処理はどうなるのでしょうか。

処理ごとに実行する周期が異なる場合はどうでしょうか。

複数の処理に優先順位を付けたい場合は？

こうした問題を解決する方法の1つが、**マルチタスクOS**です。

## タスクとは何か？

タスクとは、OSが実行を管理する処理の単位です。

普通のCプログラムでは、関数を呼び出すと、その関数が終了するまで呼び出し元には戻りません。

一方、マルチタスクOSでは、複数のタスクを用意し、それぞれを独立した処理として扱えます。

例えば、次のような構成です。

- タスクA：LEDを点滅させる
- タスクB：ボタン入力を監視する
- タスクC：センサの値を取得する

これらのタスクは、必ずしも同時に実行されるわけではありません。

CPUが1つの場合でも、OSが実行するタスクを切り替えることで、複数の処理が並行して進んでいるように動作させられます。

ここで重要なのは、**アプリケーション側で処理の切替をすべて管理しなくてもよい**という点です。

もちろん、OSを使わずに同様の仕組みを自作することも可能です。しかし、それはOSが提供する機能の一部をアプリケーション側で実装することになります。

## Try Kernelのタスク管理機能

Try Kernelでは、タスク管理のために3つのAPIを用意しています。

| API | 機能 |
|---|---|
| `tk_cre_tsk` | タスクの生成 |
| `tk_sta_tsk` | タスクの実行開始 |
| `tk_ext_tsk` | 自タスクの終了 |

いずれも、アプリケーションからC言語の関数として呼び出します。

### タスクを生成する：tk_cre_tsk

```c
ID tk_cre_tsk(const T_CTSK *pk_ctsk);
```

タスクを生成するAPIです。

引数には、タスクの実行関数やスタック領域などを指定するためのタスク生成情報を渡します。

生成に成功すると、OSが割り当てたタスクIDが返されます。

ただし、**タスクを生成しただけでは実行は始まりません。**

生成直後のタスクは休止状態です。

### タスクの実行を開始する：tk_sta_tsk

```c
ER tk_sta_tsk(ID tskid, INT stacd);
```

生成済みのタスクを実行可能な状態にするAPIです。

`tskid`には、`tk_cre_tsk`で取得したタスクIDを指定します。

`stacd`はタスクの実行開始時に渡すパラメータですが、Try Kernelではサポートしていません。

ここで注意したいのは、**実行開始を指示したタスクが、その瞬間にCPUで動き始めるとは限らない**ことです。

実際にどのタスクが実行されるかは、OSのスケジューリングによって決まります。

### タスクを終了する：tk_ext_tsk

```c
void tk_ext_tsk(void);
```

現在実行中のタスク自身を終了するAPIです。

このAPIを呼び出すと、タスクは休止状態になります。

終了したタスクは、`tk_sta_tsk`によって再び実行を開始できます。

また、`tk_ext_tsk`は呼び出し元に戻りません。

## タスクの生成・実行・終了を整理する

ここまでの3つのAPIの関係を整理すると、次のようになります。

```text
タスク未生成
    |
    | tk_cre_tsk()
    v
  休止状態
    |
    | tk_sta_tsk()
    v
  実行可能状態
    |
    | OSが実行するタスクを選択
    v
  実行状態
    |
    | tk_ext_tsk()
    v
  休止状態
```

これは今回の3つのAPIに注目した簡略図です。実際のタスクには待ち状態などもありますが、それらは次の記事で扱います。

ここで興味深いのは、**タスクの生成と実行開始が別々のAPIになっていること**です。

タスクを生成しただけでは動きません。アプリケーションが明示的に実行開始を指示する必要があります。

この仕組みにより、複数のタスクをあらかじめ生成しておき、必要なタイミングで実行を開始できます。

## なぜOSが必要なのか？

今回取り上げたタスク管理は、マルチタスクOSの基本となる機能です。

OSがなくても、複数の処理を実行するプログラムは作れます。

しかし、その場合は、どの処理をいつ実行するか、ほかの処理との関係をどう管理するかを、アプリケーション側で考える必要があります。

マルチタスクOSを使うと、それぞれの処理をタスクとして分離し、実行の管理をOSに任せられます。

そのため、アプリケーション開発者は、個々の処理の内容やタスク間の連携に集中しやすくなります。

ただし、タスクを分離するだけですべての問題が解決するわけではありません。

複数のタスクが動き始めると、今度は「あるタスクの処理が終わるまで、別のタスクを待たせたい」といった要求が出てきます。

そこで必要になるのが、次に取り上げる**タスク付属同期機能**です。

## おわりに

今回は、Try Kernelが提供するタスク管理機能について、3つのAPIを中心に整理しました。

- `tk_cre_tsk`：タスクを生成する
- `tk_sta_tsk`：タスクの実行を開始する
- `tk_ext_tsk`：タスクを終了する

マルチタスクOSを使うことで、複数の処理をタスクとして分離し、その実行をOSに管理させられます。

次回は、タスクを待たせたり起こしたりする「タスク付属同期機能」を使ってみます。
