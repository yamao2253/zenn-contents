## はじめに

Try Kernelは、CQ出版社『Interface』2023年7月号の特集「ゼロから作るOS」のために開発された、マイコン向けの超軽量リアルタイムOSです。

リアルタイムOSの基本的な機能に絞って実装されており、約1500行のC言語でOSの仕組みを学べるようになっています。

これまで私は、Windows上にTry Kernelの開発環境を構築し、同誌の記事に沿ってRaspberry Pi Picoで実際に動かしてみました。  
※ 開発環境の構築手順については、[こちらの記事](https://zenn.dev/helowota/articles/pico-trykernel-windows-env)で紹介しています。

同誌はリアルタイムOSを「作る」ことが中心ですが、その仕組みを深く理解するには、まずリアルタイムOSがどのようなもので、アプリケーションからどう「使う」のかを理解しておくことが大切だと考えました。

そこで今回は、Try Kernelが提供する機能をアプリケーションから使いながら、リアルタイムOSの役割や必要性を学んでいきます。

リアルタイムOSでは、複数の処理をタスクとして管理し、それらを適切なタイミングで実行することが基本となります。さらに、タスク同士が協調して動作するためには、待ち合わせや情報の通知、共有資源の管理といった仕組みも重要です。

Try Kernelでは、こうした基本的な仕組みを学ぶために、次の4つの主要機能が用意されています。

| 機能 | 役割 |
|---|---|
| タスク管理 | 複数の処理をタスクとして実行する |
| タスク付属同期 | タスクを待たせたり、起こしたりする |
| イベントフラグ | タスク間でイベントを通知する |
| セマフォ | 共有資源へのアクセスを制御する |

これらの機能が必要となる理由や、アプリケーションからの使い方を、実際にTry Kernelを動かしながら紹介していきます。

本記事では、最初の「タスク管理」を取り上げ、Try KernelのAPIを実際に使いながら考えていきます。

## OSがなくてもプログラムは動くが…

Raspberry Pi Picoでは、OSを使わなくてもC言語でプログラムを作れます。

例えば、LEDを点滅させるプログラムなら、無限ループの中でLEDのON/OFFを繰り返せば実現できます。

では、LEDを点滅させながら、ボタンの入力も監視したい場合はどうでしょうか。

これもOSがなくても実現できます。LEDの制御とボタンの監視を、1つのループの中で順番に実行すればよいのです。

しかし、処理が増えてくると、少しずつ難しくなります。

LEDの点滅、ボタンの監視、センサからのデータ取得など、それぞれの処理をどのような順番で実行するのか。処理ごとに実行する周期が異なる場合はどうするのか。優先順位を付けたい場合はどうするのか。

OSを使わない場合、こうした実行順序やタイミングの管理も、LEDの制御やボタンの監視といった、本来実現したい処理のプログラムに組み込む必要があります。

組込みシステムでは、このような機器の機能を実現するソフトウェアを「アプリケーション」と呼びます。

もちろん、OSがなくても工夫次第で複数の処理を実現できます。しかし、処理が増えるほど、それらを管理する仕組みも複雑になっていきます。

そこで役立つのが、**マルチタスクOS**です。

複数の処理を独立した単位として扱い、その実行をOSに管理させることで、アプリケーションの構成を整理しやすくなります。

## マルチタスクとは？

マルチタスクとは、複数の処理を並行して進める仕組みです。

私たちが普段使っているパソコンでも、Webブラウザでページを表示しながら音楽を再生するなど、複数の処理が同時に動いているように見えます。

しかし、**マルチタスクだからといって、必ずしも複数の処理が同じ瞬間に実行されているわけではありません。**

CPUが1つの場合、ある瞬間に実行できる処理は基本的に1つです。OSが短い時間で実行する処理を切り替えることで、複数の処理を並行して進められます。

このとき、OSが実行を管理する処理の単位を「タスク」と呼びます。

例えば、次のようなタスクを用意したとします。

- タスクA：LEDを点滅させる
- タスクB：ボタン入力を監視する
- タスクC：センサの値を取得する

CPUが1つでも、OSが実行するタスクを切り替えることで、3つの処理を並行して進められます。

```text
時間 ────────────────────────────>

CPU   | タスクA | タスクB | タスクC | タスクA | タスクB |
```

このように実行するタスクを切り替えることを「タスク切替」と呼びます。また、どのタスクを実行するかを決める仕組みを「スケジューリング」と呼びます。

では、普通のC言語の関数とタスクは何が違うのでしょうか。

通常、関数を呼び出すと、その関数の処理が終わるまで呼び出し元には戻りません。

一方、マルチタスクOSでは、それぞれのタスクを独立した処理として扱い、OSが実行するタスクを切り替えます。タスクは実行の途中で切り替えられても、再び実行されるときには中断したところから処理を続けられます。

つまり、**アプリケーションが処理の切替をすべて管理する必要はなく、その役割をOSに任せられる**のです。

これが、マルチタスクOSの基本的な考え方です。


## Try Kernelのタスク管理機能

書籍では、第3部 第2章（P.67〜）でスケジューラやタスク管理機能の仕組みを解説しています。ここでは、その機能をアプリケーションから使う側に注目します。

Try Kernelでは、アプリケーションからタスクを扱うための機能が用意されています。タスクの切替や実行順序の管理はOSに任せ、アプリケーションはAPIを通じてタスクの生成や実行開始、終了を指示します。

タスク管理には、次の3つのAPIを使用します。

| API | 機能 |
|---|---|
| `tk_cre_tsk` | タスクの生成 |
| `tk_sta_tsk` | タスクの実行開始 |
| `tk_ext_tsk` | 自タスクの終了 |

いずれも、アプリケーションからC言語の関数として呼び出します。

### ITRON系OSとの共通点

Try KernelのAPI名はT-Kernelと共通しており、先頭の `tk_` を除くとμITRONのAPI名とも一致します。

書籍にも書かれていますが、Try Kernelは、日本のTRONプロジェクトから生まれたリアルタイムOSをベースとする国際標準規格「IEEE 2050-2018」を参考に設計されています。

Try Kernelは学習用の小さなOSですが、APIの命名だけでなく、これから登場する「休止状態」「実行可能状態」「実行状態」といった用語や、タスク管理の基本的な考え方も、ITRON系OSと共通しています。

### タスクを生成する：tk_cre_tsk

```c
ID tk_cre_tsk(const T_CTSK *pk_ctsk);
```

タスクを生成するAPIです。

引数には、タスクの実行関数やスタック領域などを指定するためのタスク生成情報を渡します。

生成に成功すると、OSが割り当てたタスクIDが返されます。このタスクIDは、後で `tk_sta_tsk()` などのAPIから対象のタスクを指定するために使用します。

ただし、**タスクを生成しただけでは実行は始まりません。**

生成直後のタスクは「休止状態」となります。休止状態とは、タスクは生成されているものの、実行が開始されていない、または実行を終了した状態です。

### タスクの実行を開始する：tk_sta_tsk

```c
ER tk_sta_tsk(ID tskid, INT stacd);
```

休止状態のタスクの実行を開始するAPIです。

`tskid`には、`tk_cre_tsk`で取得したタスクIDを指定します。

`stacd`はタスクの実行開始時に渡すパラメータですが、Try Kernelではサポートしていません。

このAPIを呼び出すと、指定したタスクは休止状態から「実行可能状態」になります。

実行可能状態とは、実行する準備が整い、CPUが割り当てられるのを待っている状態です。

ここで注意したいのは、**実行開始を指示したタスクが、その瞬間にCPUで動き始めるとは限らない**ことです。

OSのスケジューリングによってCPUが割り当てられると、タスクは「実行状態」となり、実際に処理を開始します。

`tk_sta_tsk()` は、正常終了またはエラーを示すコードを `ER` 型で返します。書籍のサンプルコードでは戻り値を確認していませんが、今回はタスク管理の基本動作を理解することを目的としているため、エラー処理には踏み込みません。実際のアプリケーションでは、戻り値を確認してエラーに対処する必要があります。

### タスクを終了する：tk_ext_tsk

```c
void tk_ext_tsk(void);
```

現在実行中のタスク自身を終了するAPIです。

このAPIを呼び出すと、タスクは実行状態から休止状態に戻ります。

終了したタスクは、`tk_sta_tsk()` によって再び実行を開始できます。

また、`tk_ext_tsk()` は呼び出し元に戻りません。

今回のTry Kernelでは、別のタスクを指定して強制終了するAPIは実装されていません。

## タスクの生成・実行・終了を整理する

ここまでの3つのAPIと、タスクの状態の関係を整理すると、次のようになります。

```text
タスク未生成
    |
    | tk_cre_tsk()
    v
  休止状態
    |
    | tk_sta_tsk()
    v
  実行可能状態
    |
    | OSがCPUを割り当てる
    v
  実行状態
    |
    | tk_ext_tsk()
    v
  休止状態
```

これは今回の3つのAPIに注目した簡略図です。実際のタスクには待ち状態などもありますが、それらは次の記事で扱います。

ここで注目したいのは、**タスクの生成と実行開始が別々のAPIになっていること**です。

タスクを生成しただけでは動きません。アプリケーションが明示的に実行開始を指示する必要があります。

この仕組みにより、複数のタスクをあらかじめ生成しておき、必要なタイミングで実行を開始できます。

## Try Kernelで実際に動かしてみる

ここからは、書籍P.74のリスト12「サンプル・アプリケーション」を使って、タスク管理の動作を確認します。

今回はOSの内部実装には手を加えず、アプリケーションからタスク管理APIを使用し、その動作を確認していきます。

### 使用するコードと開発環境

使用するのは、『Interface』2023年7月号の第3部 第2章に対応するTry Kernelと、P.74のリスト12「サンプル・アプリケーション」です。

ソースコードは、著者の[GitHubリポジトリ](https://github.com/ytoyoyama/interface_trykernel)で公開されています。

- 使用するディレクトリ：`part_3/sect_2`
- 対象ファイル：`application/usermain.c`

開発環境は、以下の記事で構築したWindows 11上の環境を使用します。

- [「ラズパイPicoで1500行 ゼロから作るOS」を2026年に動かす](https://zenn.dev/helowota/articles/pico-trykernel-windows-env) — 開発環境の構築からビルド・書き込みまで

今回の動作確認では、Debug ProbeのSWD経由でプログラムを書き込み、UARTからの出力をシリアル通信に対応したターミナルソフトで確認します。本記事ではTera Termを使用します。

| 項目 | 内容 |
|---|---|
| ターゲット | Raspberry Pi Pico W（RP2040） |
| ビルド | GNU Make、Arm GNU Toolchain |
| 書き込み | OpenOCD、GDB |
| UART出力の確認 | Tera Term（115200 bps、8N1、フロー制御なし、受信改行LF） |
| デバッグプローブ | Pico W（CMSIS-DAP、UART） |

今回は、`part_3/sect_2` に対応するMakefileを用意し、ビルドから実機での動作確認までを行います。

### サンプルコードの処理の流れ

`application/usermain.c` では、2つのタスクを生成・起動し、それぞれのタスクから文字列を出力した後、タスクを終了します。

文字列の出力には、Try Kernelが用意している `tm_putstring()` 関数を使用します。

処理の流れを、アプリケーション側から見ていきます。

**1. `usermain()` から処理を開始する**

Try Kernelでは、OS側の `main()` が初期タスクを生成・起動し、その初期タスクから `usermain()` を呼び出します。

この仕組みは、書籍P.73〜74のリスト10・11 `kernel/inittsk.c` で説明されています。

アプリケーション側では、`usermain()` にタスクの生成や起動などの処理を記述します。

**2. `tk_cre_tsk()` で2つのタスクを生成する**

`usermain()` から `tk_cre_tsk()` を呼び出し、タスク1とタスク2を生成します。

生成に成功するとタスクIDが返されるため、それぞれ `tskid_1`、`tskid_2` に保存します。

生成されたタスクは休止状態となり、この時点ではまだ実行されません。

**3. `tk_sta_tsk()` でタスクを起動する**

続いて `tk_sta_tsk()` に取得したタスクIDを指定し、それぞれのタスクを実行可能状態にします。

ただし、実行可能状態になったタスクが直ちに実行されるとは限りません。実際の実行順序は、タスクの優先度とOSのスケジューリングによって決まります。

今回のサンプルでは、初期タスクの優先度が高いため、`usermain()` の実行中は初期タスクが処理を続けます。

**4. 各タスクが文字列を出力して終了する**

初期タスクが終了すると、実行可能状態になっていたタスクが実行されます。

各タスクでは文字列を出力し、`tk_ext_tsk()` で自タスクを終了します。

終了したタスクは休止状態に戻り、OSは次に実行するタスクを選択します。

このサンプルでは、タスクの生成、実行開始、終了という一連の流れを確認できます。

なお、この段階のTry Kernelには、タスクを待ち状態にする機能はまだ実装されていません。そのため、今回はタスクを順番に実行する動作を確認します。

### 実機で確認すること

書籍のサンプルコードを変更せずにビルドし、Raspberry Pi Pico Wで動作を確認します。

今回は、UARTの出力から、次の順序で処理が進むことを確認します。

1. `usermain()` から文字列が出力される
2. タスク1から文字列が出力される
3. タスク2から文字列が出力される

また、ソースコードと実行結果を照らし合わせ、タスクの生成・起動・終了という一連の流れを確認します。

### ビルドと実機での動作確認

著者のソースコード `part_3/sect_2` に、Windows環境でビルドするためのMakefileを追加します。Try Kernelのソースコード自体は変更しません。

`part_3/sect_2` ディレクトリに、以下の内容で `Makefile` を作成してください。

このMakefileは、前回の記事で構築した開発環境を前提としており、mkdir や rm などのコマンドを使用します。

```makefile
# Try Kernel - Part 3, Section 2 (RP2040)

TARGET := trykernel
CC := arm-none-eabi-gcc
SIZE := arm-none-eabi-size
OBJDUMP := arm-none-eabi-objdump

CFLAGS := -mcpu=cortex-m0plus -mthumb -O0 -ffreestanding -std=c99 -Iinclude -g
LDFLAGS := -mcpu=cortex-m0plus -mthumb -T linker/pico_memmap.ld -nostartfiles

SRCS := boot/boot2.c \
        boot/reset_hdr.c \
        boot/vector_tbl.c \
        kernel/syslib.c \
        kernel/context.c \
        kernel/inittsk.c \
        kernel/scheduler.c \
        kernel/task_mange.c \
        kernel/task_queue.c \
        application/usermain.c

ASRCS := kernel/dispatch.S

OBJS := $(patsubst %.c,build/%.o,$(SRCS)) \
        $(patsubst %.S,build/%.o,$(ASRCS))

ELF := build/$(TARGET).elf

.PHONY: all clean size sections

all: $(ELF)

$(ELF): $(OBJS) linker/pico_memmap.ld
	$(CC) $(LDFLAGS) -o $@ $(OBJS)
	$(SIZE) $@

build/%.o: %.c
	@mkdir -p $(dir $@)
	$(CC) $(CFLAGS) -c $< -o $@

build/%.o: %.S
	@mkdir -p $(dir $@)
	$(CC) $(CFLAGS) -c $< -o $@

size: $(ELF)
	$(SIZE) $(ELF)

sections: $(ELF)
	$(OBJDUMP) -h $(ELF)

clean:
	rm -rf build
```

:::message
Makefileのコマンド行は、行頭をスペースではなくタブにしてください。
:::

PowerShellで `part_3/sect_2` に移動し、以下を実行します。

```powershell
make clean
make
```

正常にビルドできると、`build/trykernel.elf` が生成されます。

今回の環境では、次の結果になりました。

```text

   4505      60    3416    7981    1f2d build/trykernel.elf
```
続いて、Debug Probeを接続し、OpenOCDを起動します。


別のPowerShellからGDBを起動します。


GDBで以下を実行し、プログラムを書き込みます。

```text
target remote localhost:3333
```

書き込み後、UART出力を受信できる状態にしてから、GDBでプログラムを実行します。

```text

```

実行結果は、次の「シリアル出力を確認する」で紹介します。

### シリアル出力を確認する

Try Kernelの起動メッセージやタスクからの文字列出力は、Debug ProbeのUART経由で確認します。

Tera Termを起動し、Debug Probeのシリアルポートを選択します。今回の環境では `COM5` を使用しました。

通信条件は次のとおりです。

| 項目 | 設定値 |
|---|---|
| 通信速度 | 115200 bps |
| データ長 | 8 bit |
| パリティ | none |
| ストップビット | 1 bit |
| フロー制御 | NONE |
| 受信改行コード | **LF** |

**「設定」→「端末」の受信改行コードは `LF` に設定してください。**

今回のプログラムはLF（`\n`）のみを出力するため、`CR` や `CR+LF` に設定すると、文字列が階段状に表示されます。

正しく設定すると、次の出力が得られます。

```text
Strat Try Kernel
Start user-main
Start Task-1
Start Task-2
```

最初の `Strat Try Kernel` は、OS側の `kernel/inittsk.c` にある初期タスク `initsk()` が出力しています。

Try Kernelでは、`main()` が初期タスクを生成・起動し、初期タスクの中でシリアル通信を初期化してから、このメッセージを出力します。その後、`usermain()` を呼び出してアプリケーションの処理に移ります。

続く `Start user-main` は `usermain()`、`Start Task-1` と `Start Task-2` は、それぞれのタスクからの出力です。

なお、`Strat` は元のソースコードの表記をそのまま掲載しています。

### 実機で動かして分かったこと

実行結果から、`usermain()` の処理後にタスク1、タスク2が順番に実行されることを確認できました。

ここで注目したいのは、**`tk_sta_tsk()` でタスクを実行可能状態にしても、直ちにそのタスクが実行されるとは限らない**という点です。

今回のサンプルでは、初期タスクの優先度がタスク1、タスク2より高いため、`usermain()` の処理が継続されます。

`usermain()` から戻ると、初期タスクは `tk_ext_tsk()` を呼び出して終了します。その後、実行可能状態になっていたタスク1、タスク2が順番に実行されます。

つまり、**タスクを実行可能状態にすることと、実際にCPUが割り当てられて実行されることは別**です。

どのタスクを実行するかは、OSのスケジューラがタスクの優先度などに基づいて決定します。

---

## おわりに

今回は、Try Kernelのタスク管理機能を使って、タスクの生成・起動・終了という一連の動作を実機で確認しました。

マルチタスクOSを使うことで、複数の処理をタスクとして分離し、その実行をOSに管理させられることが分かりました。

ただし、複数のタスクを動かすには、実行順序の管理だけでは不十分です。例えば、あるタスクの処理が終わるまで、別のタスクを待たせたい場合もあります。

次回は、こうしたタスク間の連携に必要となる**タスク付属同期機能**を取り上げます。
